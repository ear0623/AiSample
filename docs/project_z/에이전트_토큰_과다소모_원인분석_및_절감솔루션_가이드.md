# 에이전트 토큰 과다소모 원인분석 및 절감솔루션 가이드

> 작성일: **2026-11-09** (모델명·가격·기본값은 이 날짜의 공식 문서 기준)
> 문제: 외부 에이전트(Claude Opus 5.5 / Claude Code / MCP)로 **작업 1회에 주간 토큰 7% 이상**이 소모된다.
> 목표: 원인을 구조적으로 분해하고, **같은 작업을 80~95% 적은 토큰으로 끝내는 절차**를 수치와 함께 고정한다.
> 관련 문서: [`../mcp_token_optimization_guide.md`](../mcp_token_optimization_guide.md) — MCP 도구 정의·페이로드 최적화는 그쪽에서 다룬다. 이 문서는 **에이전트 루프 자체**(턴 수 × 컨텍스트 × 출력)를 다룬다.

---

## 0. 3줄 요약

1. **비용은 "대화 길이"가 아니라 "턴 수 × 누적 컨텍스트 × 단가"의 곱이다.** 메시지 API에는 서버 상태가 없어서 매 턴 이전 대화 전체를 다시 보낸다. 20~30턴 작업의 누적 입력은 150만~300만 토큰이고, 이 값은 턴 수의 **제곱**으로 커진다.
2. **7%를 만드는 결정적 변수는 턴 수가 아니라 캐시다.** 같은 30턴이라도 프롬프트 캐시가 매 턴 살아 있으면 약 $6.5, 매 턴 깨지면 약 $14.5다(목록가 기준, §1.4). 캐시 1회 미스는 80만 컨텍스트에서 **웜 턴 22개 값**이다.
3. **80~95%는 "모델을 바꿔서"가 아니라 "턴을 줄이고, 출력을 줄이고, 캐시를 지켜서" 나온다.** Opus 5.5는 Sonnet 5.5의 2배일 뿐이므로 모델 교체만으로는 최대 50%다. §4의 6개 조치를 곱하면 모델 계산상 90% 이상, 보수적으로 잡아도 80% 이상이 사라진다.

| 단계 | 조치 | 줄어드는 항 | 이 문서의 근거 수치 |
| --- | --- | --- | --- |
| 1 | 1작업 1세션 + 마이크로 인계서 | 턴 수 N | 30턴 → 10턴: 입력 3.03M → 0.41M (−86%) |
| 2 | 부분 읽기·출력 절제 | 턴당 증가분 h, 출력 | h 6,000 → 2,500 (−58%) |
| 3 | 모델·effort 분리 | 단가 계수 | Opus → Sonnet 50%, effort high → medium |
| 4 | 캐시 핀(접두사 고정) | 캐시 쓰기 배수 | 웜 유지 시 입력 비용 −55% |
| 5 | MCP·도구 정의 축소 | 고정비 D | 131도구 46,273 → 843토큰(Claude Code 실측) |
| 6 | deny 규칙·CLAUDE.md 다이어트 | 재읽기·재시도 | 무제한 재읽기 제거 |

## 1. 문제 정의: "작업 1회 = 주간 7%"는 무엇을 뜻하는가

### 1.1 주간 한도의 구조 (Anthropic이 공개한 사실)

- 유료 플랜은 **두 개의 계량기**를 동시에 돌린다. 5시간 세션 한도와, 계정마다 고정된 시각에 리셋되는 **주간 한도**다.
- 주간 한도는 **모든 모델 합산**이며 `claude.ai`, Claude Code, Claude Desktop이 **같은 한도를 공유**한다. 그래서 "코드만 조금 썼는데 웹 채팅이 막히는" 일이 생긴다.
- Anthropic은 **절대 토큰량을 공개하지 않는다.** 공개된 것은 구조(5시간 + 주간, 고정 리셋)와 플랜 배수뿐이다. 2026-09-14부터 Claude Code 주간 한도는 프로모션 이전 기준의 **125%**로 영구 상향됐다.
- 따라서 "7%"는 **사용자 계정의 주간 계량기에서 7포인트**를 뜻하며, 토큰 절대량은 `/usage`의 분해로만 확인할 수 있다.

> 실무 해석: 7%는 "토큰 7%를 썼다"가 아니라 "이번 주 쓸 수 있는 양의 7%를 이 작업 하나가 먹었다"이다. 같은 주에 이런 작업을 14번 하면 주간 한도가 끝난다. 이것이 체감 문제의 실체다.

### 1.2 토큰은 어디로 가는가 — 실제 감사 사례

한 개발자가 Claude Code 한 플랜을 일주일 굴린 뒤 로컬 트랜스크립트 전체(2,914개 파일)를 집계한 공개 감사(2026-11-07)가 있다. 숫자가 원인을 그대로 보여준다.

| 항목 | 값 | 의미 |
| --- | --- | --- |
| 주간 총 토큰 | **95억** | 그중 **96%가 캐시 읽기** |
| API 목록가 환산 | $4,509 | 실제 청구액은 아님(정액제) |
| 모델 점유 | **Opus 5.5가 98.1%** | Sonnet 1.9%, Haiku 0% |
| 비용 구성 | 캐시 읽기 40.5%, 캐시 쓰기 36.2%, 출력 23.2% | 순수 입력은 1달러 미만 |
| 메인 대화 1회 호출 | 평균 컨텍스트 **43.1만 토큰**, $0.126 | 대화가 길수록 호출당 단가 상승 |
| 워크플로 에이전트 | 전체의 **58.9%** (166회 실행, 2,169 에이전트) | 내가 친 메시지가 아니라 **내가 띄운 에이전트**가 청구서를 만들었다 |
| Bash 출력 | **1억 8,900만 자 / 51,949회 = 전체 도구 출력의 84%** | 컨텍스트에 그대로 들어가 **이후 모든 호출에서 다시 읽힘** |
| 최장 세션 | 컨텍스트 **96.7만 토큰** | 45만에서 컴팩션했다면 약 $166 절감(추정) |

이 표에서 읽어야 할 세 줄:

1. **대화가 아니라 루프가 돈을 쓴다.** 2,169개의 서브에이전트가 메인 대화보다 2.4배를 썼다.
2. **도구 출력이 컨텍스트를 오염시키고, 그 오염이 매 턴 재과금된다.** 명령 출력 하나가 5만 토큰이면 남은 20턴 동안 100만 토큰이 된다.
3. **캐시가 없었다면 청구서는 7배였다.** 같은 감사에서 "캐시가 없었으면 약 $34,000 추가"라고 계산한다. 즉 캐시는 이미 절감의 대부분을 담당하며, **캐시가 깨지는 순간이 유일한 대형 사고**다.

### 1.3 왜 누적되는가 — 메시지 API는 상태가 없다

Anthropic 문서가 직접 말한다. "매 턴 세 가지를 보낸다: 지금까지의 대화 전체, 프로젝트 컨텍스트(CLAUDE.md와 읽은 파일), 새 프롬프트. **이 중 첫 번째가 가장 빨리 커진다.**"

따라서 턴 `i`에서 보내는 입력은 `H_i = i · h`(h = 턴당 평균 증가분)이고, 총 입력은

```
T_total = Σ(i=1..N) (D + H_i) = N·D + h·N(N+1)/2
```

- `N·D` = **고정비** (시스템 프롬프트 + 도구 스키마 + CLAUDE.md). 턴 수에 비례.
- `h·N(N+1)/2` = **변동비**. 턴 수의 **제곱**에 비례. 여기가 진짜 범인이다.

### 1.4 숫자로 보는 7% (가정을 명시한 모델 계산)

가정: 시스템+도구+CLAUDE.md `D = 8,000`, 턴당 증가 `h = 6,000`(파일 1개 + 명령 출력 2~3개), 출력 4,000/턴(사고 토큰 포함), Opus 5.5 목록가($4 입력 / $0.20 캐시 읽기 / $8 1시간 캐시 쓰기 / $20 출력).

| 턴 | 누적 입력 | 턴당 컨텍스트(마지막) |
| --- | --- | --- |
| 1 | 14,000 | 14,000 |
| 10 | 410,000 | 68,000 |
| 20 | 1,420,000 | 128,000 |
| 30 | 3,030,000 | 188,000 |

| 시나리오 | 누적 입력 | 출력 | 캐시 | 목록가 비용 | Pro 주간 대비* |
| --- | --- | --- | --- | --- | --- |
| A. 20턴, 캐시 85% 적중 | 1.42M | 80k | 웜 | **$3.6** | 1.8% |
| B. 20턴, 매 턴 콜드 | 1.42M | 80k | 콜드 | $7.3 | 3.6% |
| C. 30턴, 매 턴 콜드 | 3.03M | 120k | 콜드 | **$14.5** | **7.3%** |
| D. 30턴, 콜드, Sonnet 5.5 | 3.03M | 120k | 콜드 | $7.3 | 3.6% |
| E. 30턴 + 서브에이전트 3개 팬아웃 | ~9M | 200k | 콜드 | $40 내외 | 20% 내외 |

\* Pro 주간을 목록가 약 $200 상당으로 환산(제3자 추정: Ultra 실측 170억 캐시읽기/주 → Pro 17억)한 값. **Anthropic은 절대량을 공개하지 않으므로 이 열은 추정이다.**

**결론: "30턴 + 캐시 미스"가 정확히 7%대다.** 즉 사용자가 겪는 현상은 우연이 아니라, 30턴짜리 긴 세션에서 캐시가 계속 깨질 때 나오는 **정상 계산 결과**다. 그리고 **같은 30턴에서 캐시만 살려도 55%**(§4), **모델을 Sonnet으로 내리면 50%**(C→D), **턴을 20으로 줄이고 캐시를 살리면 75%**(C→A)가 사라진다. 세 개를 곱하면 94%다.

### 1.5 토크나이저 인플레이션 — 같은 글이 30% 더 비싸졌다

Claude 4.7 이후 모델은 새 토크나이저를 쓰며, **같은 텍스트에 대해 토큰을 약 30% 더 많이 센다**(Anthropic 가격 문서). 2025년 블로그에 있는 "이 작업은 100만 토큰" 같은 수치를 2026년 모델에 그대로 대입하면 30% 어긋난다. `/usage`의 퍼센트가 예전 체감보다 빨리 오르는 이유의 일부다.

## 2. 5대 근본 원인

각 원인은 **진단 신호 → 실측 근거 → 처방** 순서로 적는다. 처방 번호는 §3의 솔루션 번호다.

### R1. 컨텍스트 무한 누적 (No Compaction, No /clear)

- **진단 신호**: `/context`에서 대화 비중이 50% 초과. 세션 하나가 반나절 이상 유지됨. `/usage`에 "long context" 경고가 10%를 넘음.
- **근거**: Anthropic은 "긴 세션은 매 메시지마다 그 전체를 다시 낸다"고 명시하고, `/clear`를 "품질과 비용 모두에서 가장 효과적인 단일 레버"라고 부른다. 감사 사례에서도 최장 세션이 96.7만 토큰까지 갔고, 45만에서 끊었으면 $166이 사라졌다.
- **처방**: S1, S6

### R2. 도구 출력 폭탄 (Tool Payload Bombing)

- **진단 신호**: 명령 출력이 잘리지 않고 그대로 들어옴. 1,000줄 문서를 통째로 읽음. `ls -R`, `cat` 대형 파일, 빌드 로그 전체.
- **근거**: 감사 사례에서 **Bash가 전체 도구 출력의 84%(1억 8,900만 자)**. 게다가 Claude Code는 MCP 도구 출력이 **25,000토큰(기본 상한)** 을 넘으면 자르지만, 그 아래 2만 토큰짜리 응답은 그대로 통과시킨다. 한 번 들어온 2만 토큰은 대화가 끝날 때까지 매 턴 과금된다.
- **처방**: S2, S5

### R3. 모델·effort 티어 미분리 (Opus 전용 운용)

- **진단 신호**: `/usage` 분해에서 Opus 비중 90%↑. 사고 토큰이 출력의 절반 이상. effort가 `high`/`xhigh` 고정.
- **근거**: Opus 5.5는 Sonnet 5.5의 **정확히 2배**($4 vs $2 입력, $20 vs $10 출력, 캐시 읽기 $0.20 vs $0.10, 2026-10-07 목록가). Anthropic도 "Opus는 턴당 Sonnet의 몇 배"라며 "일상 작업에 Opus를 쓰는 것이 한도를 비우는 가장 빠른 길"이라고 쓴다. 사고 토큰은 **출력으로 과금**되며, Opus/Sonnet/Haiku 5.5에서는 **끌 수 없다**(effort로만 조절).
- **처방**: S3

### R4. 프롬프트 캐시 미스 (Cache Invalidation & TTL)

- **진단 신호**: `/usage`에 "frequent cache misses" 경고. 긴 빌드·테스트 후 첫 턴이 유난히 비쌈. 중간에 `/compact` 또는 `/model` 전환을 했음.
- **근거**: 캐시는 **접두사(prefix) 일치**로만 적중한다. 접두사가 한 글자라도 바뀌면 그 뒤 전부가 무효다. TTL은 **구독 메인 대화 약 1시간, 서브에이전트·API 키 5분**(변경 가능). 그리고 결정적으로 — 캐시 쓰기는 1.25×(5분) / 2×(1시간)이고, 캐시 읽기는 0.05×(5.5 모델). 즉 **콜드 턴 1개 = 웜 턴 약 22개**. 80만 컨텍스트에서 콜드 턴은 주간의 0.176%, 웜 턴은 0.008%다(제3자 계량 모델).
- **처방**: S4

### R5. 고정비 과다 (MCP 스키마 · CLAUDE.md · 도구 정의)

- **진단 신호**: `/context`에서 "MCP tools"가 수만 토큰. CLAUDE.md 200줄 초과. 안 쓰는 MCP 서버가 연결된 채 방치.
- **근거**: 7개 서버·131도구 = 46,273토큰, 50+ 도구 = 약 72,000토큰. 이 고정비가 **매 턴** 실린다. 30턴이면 138만 토큰이 정의값만으로 나간다. Claude Code는 최근 도구 정의를 기본 지연 로딩하지만, `ENABLE_TOOL_SEARCH=false`이거나 도구가 컨텍스트의 10%를 넘으면 통째로 들어온다.
- **처방**: S5, S6

> **주의: 이 5개는 더해지는 것이 아니라 곱해진다.** 턴 30 × 턴당 6,000 × 콜드 × Opus × 8,000 고정비. 하나만 고쳐도 체감이 크고, 셋을 고치면 90%가 빠진다.

## 3. 6대 실전 절감 솔루션

### S1. 마이크로 인계서 기반 "1작업 1세션" — 가장 큰 레버

**원리**: 대화를 오래 유지하는 대신, **작업 단위로 세션을 끊고 상태를 마크다운 1장으로 넘긴다.** 인계서는 2,000토큰이면 충분하고, 그 2,000토큰이 30턴짜리 대화(300만 토큰)를 대체한다.

**이 저장소의 모범 사례**: [`B101_F01_F02_External_Agent_Review_20261109.md`](./B101_F01_F02_External_Agent_Review_20261109.md)는 120줄/약 2,000토큰으로 실행 가드·설계 계약·실패 이력·미승인 사항·요청 형식을 모두 담는다. 새 에이전트는 이 1장만 읽고 바로 작업에 들어갈 수 있다. **이것이 정확히 옳은 형태다.**

**규칙**

1. 작업이 바뀌면 `/clear`. 같은 주제로 이어가야 하면 `/compact 지시문`으로 남길 것을 지정한다.
2. 세션을 끊기 전에 인계서를 쓴다. 스키마는 고정한다: **결정사항 / 확정 수치·경로 / 실패한 시도와 이유 / 남은 승인 / 다음 1수**.
3. 인계서에 원문 로그를 붙이지 않는다. 경로만 적는다(`IntegrationMigration/.../v53.json`).
4. **한 세션의 턴 예산을 정한다**: 탐색 5 + 구현 10 + 검증 5 + 인계 1 = **20턴 상한**. 넘으면 끊고 인계서로 재개한다.

**기대 절감**: 30턴 → 10턴이면 누적 입력이 3.03M → 0.41M으로 **−86%**(§1.4 산식).

### S2. 부분 읽기와 출력 절제

**원리**: 컨텍스트에 들어온 것은 지울 수 없다. 들어오기 전에 자른다.

| 하지 말 것 | 할 것 |
| --- | --- |
| `cat 대형파일.md` | `sed -n '1,60p'`, `read_file(offset,limit)` |
| `ls -R` | `find . -name "*.py" -maxdepth 2 \| head -40` |
| 빌드 로그 전체 | `grep -E "error|warning" build.log \| head -30` |
| JSON 300건 전체 | 필드 3개만 뽑아 표로 (`jq -r '.[] \| [.id,.name] \| @tsv'`) |
| 문서 전체 재독 | `grep -n`으로 목차·해당 절만 |

**도구로 강제하는 방법**

- `MAX_MCP_OUTPUT_TOKENS`로 MCP 응답 상한을 낮춘다(기본 25,000 → 8,000 권장).
- **훅(hook)으로 전처리**: 10,000줄 로그를 에이전트가 읽게 하지 말고, 훅이 `ERROR`만 뽑아 수백 토큰으로 돌려준다. Anthropic이 공식으로 권하는 패턴이다.
- **스킬로 지식 주입**: 프로젝트 구조·규약을 스킬로 두면, 에이전트가 파일 10개를 읽어 알아내는 대신 즉시 컨텍스트를 얻는다.

**기대 절감**: `h` 6,000 → 2,500이면 20턴 누적이 1.42M → 0.68M(−52%).

### S3. 모델·effort 분리 — "설계는 Opus, 실행은 Sonnet"

**원리**: Opus의 값은 **판단**에 쓰고, **반복 실행**에는 쓰지 않는다.

| 단계 | 모델 | effort |
| --- | --- | --- |
| 아키텍처 결정, 교차 검토, 막힌 디버깅 | Opus 5.5 | high |
| 일반 구현·수정·테스트 작성 | **Sonnet 5.5** | medium |
| 탐색·로그 확인·이름 변경·포맷 | **Haiku 5.5** | low |
| 서브에이전트(파일 탐색, 테스트 실행) | Haiku/Sonnet | **low** (Anthropic이 명시 권장) |

- Claude Code에는 **`/model opusplan`** 이 내장되어 있다: 계획은 Opus, 실행은 Sonnet. 모델을 바꿔도 대화는 유지되지만 **캐시는 다시 써야 하므로**, 전환은 작업 경계에서 한 번만 한다.
- 사고 토큰은 출력 과금이다. `/effort medium`만으로도 수만 토큰이 줄어든다. `MAX_THINKING_TOKENS`는 5.5 계열에서 **무시된다**(적응형 추론) — effort를 써야 한다.
- 서브에이전트의 요청도 **내 한도를 소비한다.** 서브에이전트는 반드시 저가 모델·낮은 effort로 고정한다(`model: haiku`).

**기대 절감**: Opus→Sonnet 50%, effort high→medium에서 출력 30~50% 추가.

### S4. 프롬프트 캐시 핀(Pinning) — 접두사를 절대 건드리지 않는다

**원리**: 캐시는 "앞에서부터 같은가"만 본다. 접두사가 흔들리면 뒤가 전부 새로 써진다.

**지킬 것**

1. **정적 블록을 맨 앞에 고정**: 시스템 프롬프트 → 도구 정의 → CLAUDE.md(불변) → 프로젝트 규약. 이 순서와 내용을 세션 중에 바꾸지 않는다.
2. **가변 정보는 뒤로**: 오늘 날짜, 진행 상황, 임시 메모는 대화 뒤쪽에만.
3. **턴 사이 간격을 TTL 안으로**: 구독 메인 대화는 약 1시간, 서브에이전트·API는 5분. 긴 빌드(10분+)를 기다린 뒤 이어가는 패턴은 5분 TTL에서 **매번 콜드**가 된다 → 빌드는 백그라운드로 돌리고, 결과는 짧게 요약해 받는다.
4. **중간 `/compact`와 `/model` 전환을 최소화**. 둘 다 캐시를 리셋한다. 그리고 `/compact` 자체가 **대화 전체를 읽는 큰 요청**이다(캐시가 식었으면 더 비싸다). 컴팩션은 "한 단계가 끝났을 때" 한 번.
5. **도구 결과를 순서대로 정렬**해 같은 요청이 같은 접두사를 갖게 한다(MCP 서버를 직접 쓸 때).

**기대 절감**: 콜드 → 웜이면 입력 비용 **−55%**(§1.4 A vs B), 최악의 경우 턴당 **22배** 차이를 없앤다.

### S5. MCP 서버 선택적 활성화

- `/mcp`로 안 쓰는 서버를 끈다. Claude Code는 도구 정의를 지연 로딩하지만, 10% 규칙(`auto`)에 걸리면 통째로 들어온다. `/context`로 확인.
- **CLI가 있으면 CLI를 쓴다.** `gh`, `python`, `curl`은 도구 스키마를 추가하지 않는다. Anthropic도 "MCP 서버보다 CLI가 컨텍스트 효율이 높다"고 명시한다.
- 서버를 유지해야 하면 **스키마를 깎는다**(937 → 237토큰 사례). 상세는 [MCP 토큰 최적화 가이드](../mcp_token_optimization_guide.md) §2·§4.

**기대 절감**: 턴당 1.5만~3만 토큰 고정비 → 수백 토큰.

### S6. Claude Code 설정 — 무제한 재읽기를 막는다

**중요한 정정**: **`.claudeignore`는 존재하지 않는다.** 만들어도 효과가 없다(여러 곳에서 여전히 권장하지만 틀렸다). `.gitignore`는 `respectGitignore`가 켜져 있을 때 **`@` 파일 선택기에서만** 숨기고, 읽기 자체는 막지 않는다.

실제로 막는 것은 **`permissions.deny`의 `Read(...)` 규칙**이다.

```json
// .claude/settings.json (프로젝트 공용, 커밋 대상)
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "deny": [
      "Read(./Intermediate/**)",
      "Read(./Saved/**)",
      "Read(./Binaries/**)",
      "Read(./DerivedDataCache/**)",
      "Read(./.git/**)",
      "Read(./**/*.log)"
    ]
  }
}
```

- 이 규칙은 Read/Edit/Write, Grep/Glob, `@` 멘션, 그리고 Claude Code가 인식하는 `cat`/`head`/`tail`까지 막는다. 단 `grep -r`이나 스크립트가 직접 여는 것은 막지 못한다(그건 sandbox의 `filesystem.denyRead` 영역).
- **CLAUDE.md는 200줄 이하**. 매 턴 실리는 고정비다. 상세 절차는 스킬로 옮긴다(스킬은 호출될 때만 로드).
- **경로 규칙은 `.claude/rules/`에 스코프드로**: 해당 파일을 만질 때만 로드된다.

**기대 절감**: 대형 바이너리·빌드 산출물 재읽기 제거로 10~20%, 사고·재시도 감소 포함.

### S7. (도메인 특화) 반복 배치를 대화 루프에서 꺼낸다

**이 저장소의 실패 이력이 정확히 이 패턴이다.** 인계서 §5.2에 기록된 v52 실패는 "MCP로 문 Actor를 하나씩 배치 → 피벗·Bounds 오류 → 다시 배치"의 반복이었고, §7은 그 대안으로 **Anchor Cube + 백그라운드 Commandlet**을 이미 계약으로 못박아 두었다.

문 34개, 창 17개를 대화 안에서 하나씩 배치하면 **턴 34개 × 누적 컨텍스트**가 발생한다. 같은 작업을 스크립트 1회 실행으로 옮기면:

| 방식 | 대화 턴 | 누적 입력(추정) |
| --- | --- | --- |
| MCP 개별 배치 34회 | 34+ | 350만 토큰 |
| 배치 스크립트 1회 + JSON 보고서 요약 | 2~3 | 6만 토큰 |

**규칙**: "같은 종류의 액터를 3개 이상 만든다"가 판단되면, 그 즉시 대화 루프를 멈추고 **스크립트를 쓰고 한 번 실행**한다. 에이전트는 스크립트를 작성·검증하고, 결과는 JSON 요약으로만 받는다.

### 6.1 화면으로 보는 법

| 명령 | 보는 것 |
| --- | --- |
| `/usage` (별칭 `/cost`, `/stats`) | 5시간·주간 바, **스킬·서브에이전트·플러그인·MCP별 분해**. 긴 컨텍스트·캐시 미스가 10% 넘으면 경고 |

| `claude -p "/context"` | 대화 없이 점유만 확인 |

### 6.2 상태줄에 주간 잔량 상시 표시

Claude Code는 Pro/Max 구독자에게 `rate_limits.seven_day.used_percentage`를 상태줄 스크립트로 넘긴다. 작업 전후 값을 찍어두면 "이 작업이 몇 %를 먹었는지"를 매번 실측할 수 있다.

```bash
# ~/.claude/statusline.sh (개념 예시)
input=$(cat)
printf '주간 %s%% | 5시간 %s%%' \
  "$(printf '%s' "$input" | jq -r '.rate_limits.seven_day.used_percentage // "-"')" \
  "$(printf '%s' "$input" | jq -r '.rate_limits.five_hour.used_percentage // "-"')"
```

### 6.3 로컬 트랜스크립트로 사후 집계

```bash
# 프로젝트 세션 파일에서 토큰 종류별 합계
jq -r 'select(.message.usage) | .message.usage
       | [.input_tokens, .cache_read_input_tokens, .cache_creation_input_tokens, .output_tokens]
       | @tsv' ~/.claude/projects/<프로젝트>/*.jsonl \
| awk '{i+=$1; r+=$2; w+=$3; o+=$4}
       END {printf "input %d | cache_read %d | cache_write %d | output %d\n", i, r, w, o}'
```

이 네 숫자의 비율이 진단표다.

| 관찰 | 진단 | 조치 |
| --- | --- | --- |
| `cache_write`가 `cache_read`의 20% 초과 | 캐시가 계속 깨진다 | S4 |
| `output`이 `input`의 10% 초과 | 사고·설명이 과다 | S3, S2 |
| `input`(비캐시)가 큰데 `cache_read`가 작다 | 매 턴 콜드 | S4 |
| 총합이 작업마다 비슷하게 크다 | 턴 수 문제 | S1 |

```markdown
## 세션 규칙

## 인계서 스키마 (고정)
결정사항 / 확정 수치·경로 / 실패한 시도와 이유 / 남은 승인 / 다음 1수
```

## 8. 흔한 오해 바로잡기

| 흔한 말 | 사실 |
| --- | --- |
| ".claudeignore에 넣으면 안 읽는다" | **그 파일은 없다.** `permissions.deny`의 `Read(...)` 규칙을 써야 한다. |
| "Opus는 Sonnet의 5배" | 5.5 세대는 **정확히 2배**(입력 $4 vs $2, 출력 $20 vs $10). 5배는 구세대(Opus 4 계열) 기준이다. |
| "캐시 TTL은 5분" | 구독 메인 대화는 **약 1시간**, 서브에이전트와 API 키는 5분. |
| "`/compact`하면 토큰이 줄어든다" | 컴팩션 자체가 **대화 전체를 읽는 큰 요청**이다. 캐시가 식은 뒤 하면 이득이 상쇄된다. 단계 경계에서 한 번. |
| "`MAX_THINKING_TOKENS=0`으로 사고를 끈다" | Opus/Sonnet/Haiku 5.5는 **끌 수 없다.** `/effort`로 조절한다. |
| "토큰 수는 예전과 같다" | 4.7+ 토크나이저는 같은 글에 **약 30% 더** 센다. |
| "서브에이전트는 공짜 병렬성" | 서브에이전트 요청도 **내 한도**를 쓴다. 게다가 콜드 스타트마다 캐시를 새로 쓴다(감사 사례: 에이전트당 약 3.4만 토큰 쓰기). |

## 9. 한계와 주의

- **Anthropic은 주간 한도의 절대 토큰량과 계량 가중치를 공개하지 않는다.** 이 문서의 "%" 환산은 제3자 실측·추정(§10의 10·11번)에 기반하며, 계정·플랜·시점에 따라 달라진다.
- 모델명·가격·명령·기본값은 **2026-11-09 기준**이다. 서비스가 갱신되면 §10의 1~7번 문서를 다시 확인한다.
- §1.4·§4의 비용은 **가정을 명시한 계산**이다. 같은 작업도 실행마다 최대 30배까지 토큰이 달라진다는 측정(arXiv 2604.22750)이 있으므로, 절감률은 **같은 조건의 전후 비교**(§6.3)로 확인해야 한다.
- 이 문서는 **비용·한도**를 다룬다. 정확도가 목적이면 이야기가 다르다: 토큰을 줄이면 품질이 떨어질 수 있고, 반대로 토큰 사용량이 성능 변동의 80%를 설명한다는 Anthropic 보고도 있다. **"싼 모델로 낮은 effort"는 탐색·기계적 수정에만** 쓰고, 판단이 필요한 지점은 Opus로 되돌린다.
